## 一、结论先行

- 上线前最危险的不是页面缺少，而是支付前出现互相矛盾的信息：快递、运费、商品数量能力和待付款恢复均未闭环。

## 二、建议先统一的产品模型

**核心对象：**草稿（可继续编辑）→ 已保存设计（用户资产）→ 可售方案（规格完整、可计价）→ 购物车项（商品级选项已确认）→ 订单（地址、配送、金额与支付状态已确认）。

**当前症结：**现版本在点击“加入购物车”时一次性跨过“保存设计”和“生成可售方案”，结算页又重新解释配送与金额，因此每个页面都像是对的，串起来却互相冲突。

1. 用户先创作；在离开或登录前，本地草稿必须可恢复。

2. 用户主动点击“保存设计”后，得到可命名、可再次编辑的账户资产。

3. 只有满足所选交付方式的完整性规则后，设计才可加入购物车。

4. 制作方式、包装、绳色属于商品项；地址、快递、优惠和备注属于订单。

5. 订单创建后必须可在“我的订单”继续支付、查询物流或发起售后。

## 四、P0 问题详解

> **处理原则：** P0 不建议靠补文案绕过。先确定业务规则，再统一页面入口、状态和接口含义；任何支付金额、规格或权限仍有两种解释时，都不应进入正式发布。

### P0-01 把“保存设计”和“加入购物车”拆成两个明确动作

**当前表现：**DIY 工具栏有保存图标但没有实际行为；点击“加入购物车”后，系统先保存设计，再加购，并提示“设计已按后端材料价格保存”。

**产品判断：**用户会产生三个无法回答的问题：现在是否已经保存？加购后修改的是原方案还是副本？重复加购是否会多出多条“我的设计”？

**建议方案：**建议主操作为“保存设计”，成功后提供“加入购物车 / 继续编辑”两个后续动作；若希望少一步，可在首次加购时明确提示“将保存为一个新设计并加入购物车”，以后再次加购复用同一设计版本。

**验收口径**

- 保存按钮有清晰可见的可用、保存中、已保存和有未保存修改四种状态。

- 加入购物车不会在用户不知情时创建重复设计；版本复制必须有明确提示。

- “我的设计”可看到与 DIY 中一致的名称、规格、更新时间和后续操作。

### P0-02 建立“可售方案”校验，不让半成品进入成品订单

**当前表现：**DIY 只判断是否至少有 1 颗珠子即可加购；“收拢成串”要求至少 8 颗，但加购并不要求已经成串；商品选项里又可选择“串好成品”。

**产品判断：**编辑器允许存在的状态，不等于工场可制作和交付的状态。缺少这一层会把创作自由直接变成生产风险。

**建议方案：**根据交付方式设两套规则：购买散珠包可允许未成串，但必须给出清单；购买串好成品则必须满足珠数、总周长、手围适配、配件方向和库存等校验。校验不通过时给出可修复的原因。

**验收口径**

- “自己动手”和“串好成品”各自有明确、可配置的可售条件。

- 不满足条件时按钮不可直接提交，并告诉用户缺什么、如何修改。

- 购物车和订单均保留已校验的设计快照，后续编辑不会静默改变已购商品。

### P0-03 让手围成为真实规格，而不是视觉控件

**当前表现：**用户可选择 13–21 cm 手围，但该值只显示在工具栏；页面顶部推荐范围仍由珠子自动计算，保存设计和下单也没有携带用户手围。

**产品判断：**手围是定制手串最关键的履约参数之一。当前控件会让用户误以为系统已经按手围调整，实际结果却没有变化。

**建议方案：**推荐把手围设为“目标值”，实时显示当前设计与目标的差距（偏短 / 合适 / 偏长）。串好成品必须确认手围；散珠包可以选填。保存设计、购物车快照和订单都需保留该规格。

**验收口径**

- 选择手围后，顶部状态立即反映匹配结果，而不是同时显示另一套无关推荐。

- 成品模式未确认手围时不能完成加购或结算。

- 订单详情明确展示净手围、成品预留量和最终制作规格。

### P0-04 / P0-05 分离商品选项和订单选项，并统一配送展示

**当前表现：**加购前一次选择制作方式、包装、绳色和快递；自己动手时仍展示绳色。确认订单又固定写“圆通包邮”，而购物车选项可能是韵达或顺丰并带费用。

**产品判断：**同一个订单在不同页面出现不同承运商和费用，是支付信任的直接破坏；选项依赖没有处理，也会让用户为无效字段做选择。

**建议方案：**商品项只保留制作方式、包装和必要的绳色；绳色仅在成品模式展示。配送方式移到确认订单，在选择地址后展示可达服务、时效与运费。所有金额使用同一计价结果。

**验收口径**

- 购物车、确认订单、支付金额和订单详情中的配送名称、费用完全一致。

- 选择“自己动手”时不要求绳色，且不会计入绳色费用。

- 更换地址后配送选项与运费可重新计算，用户需要主动确认变化。

### P0-06 购物车能力必须与结算能力一致

**当前表现：**购物车支持多商品勾选、全选和合计，只有点击结算时才提示第一阶段只能结算一个设计。

**产品判断：**如果当前后端只能单商品下单，前端就不应先承诺多商品任务；如果购物车保留多项，也应在选择第二项时立即解释限制。

**建议方案：**推荐最终支持多设计一单；如果短期必须单商品，先移除全选和多项合计，结算按钮直接针对当前商品，或在勾选第二项时替换选择并说明。

**验收口径**

- 用户在进入结算前就知道本单可包含多少个设计。

- 购物车展示的选中数量和合计，必然能在下一页按同样范围结算。

- 数量、选项费、运费在前后端遵循同一计价规则。

### P0-07 待付款订单必须可继续支付

**当前表现：**取消支付后页面提示订单仍保留为待支付；但“我的订单”中只有售后相关动作，没有继续支付或取消订单。离开确认页后，也没有从订单恢复支付上下文。

**产品判断：**“订单已保留”却无法继续处理，会制造死单；用户重走购物车还可能再次创建订单。

**建议方案：**订单创建成功即跳转到订单支付页或订单详情；待付款订单提供“继续支付 / 取消订单”。重复进入支付必须复用原订单，并显示关闭时间。

**验收口径**

- 取消支付后，从“我的订单—待付款”能继续支付同一订单。

- 重复点击、退出重进和弱网重试不会创建重复订单。

- 支付成功后进入成功结果页，并可查看订单详情；购物车清理结果不影响支付确认。

### P0-08 用一套登录策略覆盖“我的”、购物车和受保护动作

**当前表现：**未登录时“我的”下的个人资料、设计、订单、地址、售后全部保持正常入口样式；进入后各页面分别处理。购物车没有独立登录态，公开详情页也会主动请求需要登录的购物车。

**产品判断：**从源码看地址写接口有鉴权，本次将其定性为“权限表达和拦截时机不自洽”；若真机能匿名成功保存，则是更严重的会话或后端鉴权问题。

**建议方案：**公开浏览与受保护动作分层：可匿名浏览首页、发现、详情和 DIY；保存、加购、购物车、地址、订单在动作发生时统一拉起登录。登录成功后返回原目标继续，不让用户手动找回路径。

**验收口径**

- 未登录进入“我的”时，入口可展示价值但带锁定状态；点击直接打开统一登录层。

- 公开详情页不会因为购物车请求失败而弹出无关错误。

- 所有 401 / Token 过期都回到同一登录策略，并能恢复原页面和原动作。

### P0-09 正式用户界面不得出现测试环境说明

**当前表现：**确认订单页直接展示“测试号”“真实后端”“开发者工具”“真机配置完成后验收”等联调文字。

**产品判断：**这类内容会让用户怀疑订单、支付和个人信息是否真实，也会降低审核与发布质量。

**建议方案：**用户界面只保留业务语言；测试说明放入开发环境专用开关、日志或验收文档，生产构建不可见。

**验收口径**

- 正式构建全局搜索不到测试号、开发者工具、真实后端、联调等用户不可见词。

- 登录页和确认页均使用面向消费者的说明与失败提示。

## 五、P1 与 P2 问题的产品处理建议

### P1-01 / P1-02｜草稿与我的设计

DIY 应自动保存本地草稿；退出时仅在无法恢复的情况下提示。“我的设计”至少支持打开、继续编辑、复制、删除和加入购物车，并明确展示“草稿 / 已保存 / 已下单”状态。

### P1-03｜分享

分享必须携带可访问的设计码或只读快照。接收方先看到同一方案详情，再选择“用此方案开始 DIY”或“加入购物车”；私有方案要有授权或复制规则。

### P1-04｜地址

确认订单的地址入口应叫“选择 / 更换”，地址列表进入“本单选择模式”；设置默认是独立操作，不应是临时换地址的前置条件。

### P1-05｜订单

增加订单详情承载规格、地址、费用、制作进度和操作。统一状态口径：待付款、制作中、待发货、待收货、已完成、已取消、售后中；筛选与状态必须一一覆盖。

### P1-06｜价格

全链路统一三种价格语言：编辑中为“当前材料小计”，详情为“基础价 / 起售价”，购物车与确认页为“预计应付 / 最终应付”。任何附加费都在选择当下即时更新。

### P1-07｜购买须知与售后

在详情和确认订单展示制作周期、天然材质差异、尺寸误差、退改范围和售后流程；支付前要求用户确认。售后入口应与订单项、原因、凭证和处理进度关联。

### P1-08｜手机号授权与登录失效

基础登录与手机号绑定分开表达：先说明登录价值，再在确有履约需要时请求手机号。Token 失效统一显示“登录已过期”，完成登录后回原页面。

### P2｜信息架构与微交互

统一主功能名（建议前台统一“DIY 定制”或品牌化名称二选一）；首页和 DIY 使用同一套步骤；明确 DIY 是主 Tab 还是中心创作动作；修正“无法撤回”等反向文案，并取消人为的最低加载时长。

## 六、推荐的目标用户链路

### 1. 匿名浏览与登录

1. 匿名用户可浏览首页、发现、设计详情，也可进入 DIY 体验。

2. 首次保存、加购、进入购物车或账户数据时，统一出现登录层，并说明为什么需要登录。

3. 登录成功后恢复原页面、原设计和原动作；拒绝手机号不应等同于登录失败。

### 2. DIY 到购物车

1. 选择目标手围（成品必填）→ 挑选珠材与配饰 → 实时显示当前材料小计和匹配状态。

2. 系统自动保存本地草稿；用户主动“保存设计”后可命名并同步账户。

3. 选择购买散珠包或串好成品；系统按交付方式检查可售条件。

4. 选择商品级规格（制作、包装、必要绳色）→ 加入购物车。

5. 购物车可继续编辑规格或复制设计，但已加购项使用稳定快照。

### 3. 结算、支付与订单

1. 确认结算商品 → 选择本单地址 → 根据地址选择配送与时效 → 展示唯一应付金额。

2. 创建订单 → 拉起支付；取消后订单进入待付款，可从订单详情继续支付或取消。

3. 支付成功 → 成功结果页 → 订单详情；制作、发货、物流、收货与售后动作按状态出现。

## 七、需要产品负责人拍板的 8 个问题

1. “自己动手”到底卖散珠材料包，还是也包含绳材、工具和教程？不同答案决定绳色、手围与售后规则。

2. “串好成品”是否强制确认手围？允许的松紧量、尺寸误差和工场调整规则是什么？

3. 保存设计是否完全独立于购物车？推荐答案：独立，并以版本快照连接购物车。

4. 当前阶段是否接受单设计订单？若接受，购物车必须同步降级；若不接受，则优先完成多商品订单。

5. 配送方式是固定包邮还是用户可选？承运商、价格、时效必须由同一配置驱动。

6. 优秀客订作品是否允许他人直接购买、复制或改款？发布授权、作者展示和隐私边界是什么？

7. 定制商品的取消、退换、质量问题和天然材质差异规则是什么？需要在支付前明确。

8. 登录是否必须绑定手机号？推荐答案：基础登录不强绑，履约前按需补充并明确用途。

## 八、建议整改顺序

1. **阶段 0｜先定业务规则：**拍板上节 8 个问题；形成一页状态定义：草稿、设计、可售方案、购物车项、订单，以及商品级 / 订单级选项。

2. **阶段 1｜封住 P0 交易风险：**拆分保存与加购；接入真实手围规则；统一配送与金额；让购物车能力与结算一致；补继续支付；统一登录；移除测试文案。

3. **阶段 2｜补用户资产与回流：**草稿恢复、我的设计可继续使用、订单详情与地址选择、有效分享、购买须知和售后边界。

4. **阶段 3｜统一信息架构：**统一命名、步骤、导航语义、空状态、加载反馈和微文案，再做转化优化。

## 九、上线前产品验收清单

- 未登录用户能明确区分可浏览内容与需要登录的动作，登录后可回到原任务。

- DIY 草稿退出重进可恢复；保存、已保存修改和加入购物车的状态可区分。

- 散珠包与串好成品各自通过可售校验，成品订单包含真实手围。

- 购物车选中范围、数量、规格与下一页结算范围完全一致。

- 配送名称、时效、运费和应付金额在购物车、确认页、支付与订单中一致。

- 取消支付后可从待付款订单继续支付，同一次提交不会重复建单。

- 订单状态均有对应分组、说明和可执行动作，不出现“看得到但处理不了”的状态。

- 确认订单前已展示并确认定制商品购买须知与售后边界。

- 分享打开的是同一方案，并按权限提供查看、改款或购买动作。

- 正式构建中不存在测试账号、开发者工具、真实后端等联调文案。
